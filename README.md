# PayShield

PayShield combines two risk checks for payment websites:

1. **Website signal assessment:** a user submits a payment URL. PayShield evaluates observable URL and merchant signals, explains findings, and returns three risk reduction suggestions.
2. **IEEE-CIS transaction scoring:** the model scores transaction data only when an integration sends actual transaction features. A URL alone does not contain those features.

The app also provides account registration and sign-in, assessment history, and optional Stripe subscriptions. It does not read or intercept payments in other apps or websites, and it must not collect card numbers or CVV values.

## Current model status

The bundled IEEE-CIS model artifacts do not include all of the preprocessing artifacts used during training. Transaction scores are advisory and recommendations remain **REVIEW** until that preprocessing is restored and the model is revalidated. Do not use its output to automatically approve or decline real payments.

## Run locally

Requirements: Python 3.10+.

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
Copy-Item .env.example .env
uvicorn main:app --reload
```

Open `http://127.0.0.1:8000/app`. API documentation is at `http://127.0.0.1:8000/docs`.

The local SQLite database is stored at `data/payshield.db` by default. Keep `.env` private; it is excluded from Git and Docker build context.

### Run with Docker Compose

```powershell
docker compose up --build
```

The app is available at `http://127.0.0.1:8000/app`. Compose persists its SQLite data in the `payshield-runtime` volume.

## Deploy on Render

The repository includes [`render.yaml`](render.yaml) for a Render Blueprint. It configures a Docker web service in Singapore, a paid Standard plan with 2 GB RAM for the bundled model, a one-instance persistent disk mounted at `/app/runtime`, production mode, and generated admin and merchant API keys. The Dockerfile listens on Render's `PORT` (default `10000`).

1. Push this project to a GitHub repository. Keep `.env` out of Git; confirm it is ignored before pushing.
2. In Render, choose **New → Blueprint**, connect the repository, and apply the `render.yaml` configuration. Review the paid plan and disk before confirming.
3. Wait for the first deploy. In the service dashboard, copy its public `https://<service>.onrender.com` URL.
4. In **Environment**, set `PAYSHIELD_APP_URL` to that exact URL. Add Stripe test credentials if subscriptions are enabled:
   - `STRIPE_SECRET_KEY`
   - `STRIPE_PREMIUM_PRICE_ID`
   - `STRIPE_WEBHOOK_SECRET`
5. In Stripe test mode, create a webhook destination at `<service-url>/api/v1/billing/webhook`. Subscribe to `checkout.session.completed`, `customer.subscription.created`, `customer.subscription.updated`, and `customer.subscription.deleted`. Put that endpoint's signing secret in `STRIPE_WEBHOOK_SECRET`, save, and let Render redeploy.
6. Verify `/api/v1/health`, `/app`, registration/sign-in, URL assessment, assessment history, and a Stripe test checkout.

`render.yaml` creates a persistent disk because SQLite data must survive restarts and deploys. Render disks require a paid service, attach to one instance only, and disable zero-downtime deploys. Do not remove the disk or change its mount path without backing up the database. For multiple instances, migrate the app to a shared database such as PostgreSQL first. See [Render persistent disk documentation](https://render.com/docs/disks).

### Render environment variables

| Variable | Render setting |
|---|---|
| `PAYSHIELD_ENV` | `production` (set by Blueprint) |
| `PAYSHIELD_DB_PATH` | `/app/runtime/payshield.db` (set by Blueprint) |
| `PAYSHIELD_APP_URL` | Your deployed `https://<service>.onrender.com` URL |
| `PAYSHIELD_ADMIN_TOKEN` | Generated by Blueprint; keep private |
| `PAYSHIELD_MERCHANT_API_KEY` | Generated by Blueprint; share only with your trusted integration |
| `PAYSHIELD_FRONTEND_ORIGINS` | Blank for the bundled same-origin UI |
| `STRIPE_SECRET_KEY` | Optional Stripe test-mode secret |
| `STRIPE_PREMIUM_PRICE_ID` | Optional recurring Stripe test Price ID |
| `STRIPE_WEBHOOK_SECRET` | Optional signing secret for the deployed Dashboard webhook |
| `GOOGLE_WEB_RISK_API_KEY` | Optional; URL checks still include local URL, DNS, and TLS signals |

Never put secrets in `render.yaml`, source control, browser code, or screenshots. The Stripe CLI local forwarding secret is not the same as the deployed Dashboard webhook secret.

## API routes

All API routes use the `/api/v1` prefix.

| Method | Route | Purpose |
|---|---|---|
| `GET` | `/health` | Readiness status |
| `POST` | `/auth/register` | Create an account |
| `POST` | `/auth/login` | Sign in |
| `GET` | `/auth/me` | Read the current account |
| `POST` | `/auth/logout` | Revoke the current session |
| `POST` | `/assessments/url` | Assess a submitted payment URL (login required) |
| `GET` | `/assessments/history` | Read the user's past assessments (login required) |
| `GET` | `/assessments/{assessment_id}` | Read an assessment (login required) |
| `POST` | `/integrations/transactions/score` | Score transaction features from a trusted merchant integration |
| `POST` | `/assessments/{assessment_id}/transaction-score` | Attach a transaction score to an assessment when transaction data is available |
| `POST` | `/merchant-reports` | Submit a merchant signal report |
| `GET` | `/billing/subscription` | Read subscription status |
| `POST` | `/billing/checkout-session` | Start Stripe Checkout |
| `POST` | `/billing/portal-session` | Open Stripe Billing Portal |
| `POST` | `/billing/webhook` | Receive signed Stripe events |

Interactive API docs: `/docs`.
